# SCARS.md — operational scars (lessons from real failures)

Read this before editing anything in `scripts/**`, `hooks/**`, `skills/**`, `check_workspace_integrity.py`, `audit_*.py`, **or before any `git commit`** — the workspace-wide commit-hygiene and verification-scope scars live at the bottom, they are not script-scoped.

Extracted from the root router (`AGENTS.md`) 2026-10-04 so the router stays
terse; content below is moved verbatim, not rewritten.

- Windows tooling scars (2026-09-30): no inline `python -c` / `powershell -Command` with nested quotes or paths (MSYS mangles them) — write a file, execute it. Two failed attempts at one operation ⇒ re-plan, don't try a third variant. Set config ≠ working config: verify the artifact a capability should have produced (router model list, downstream file) before trusting it.
- Verification-tool scars (2026-10-03, from the whitespace/ARL-commit post-mortem): (d) **never hand-roll a whitespace check** — a Python test like `line.rstrip() != line.rstrip(b' \t\r\n')` is a **no-op** (both sides strip the same bytes), so it reports "clean" forever; `git diff --check` is the only authority, and it is the one that sees a space sitting *before* CRLF. Six rounds of false "(no output)" cost half an hour. (e) **A file that returns after deletion has a writer — find it before deleting again.** `$null`, `pytest.ini` and `.kilo` were three separate, undiagnosed causes; each got deleted reactively and the next session inherits the trail. (f) `git diff --cached` reads the **index**, not the working tree — after fixing files on disk, `git reset HEAD` once instead of re-editing what is already clean. (g) staged-vs-untracked confusion: a whole new file shown as `+` lines is not a duplicate-code diff.
- Executable scars (2026-10-02, from a post-mortem of the ingest/graph chore): (a) real exit code — run commands via `bash scripts/_scratch/run_and_rc.sh [-n LINES] <cmd...>`; `cmd | tail -20; echo $?` reports the pipe's rc (always 0), not the command's. (b) inspect files with `read` (offset/limit), never sed/grep — they render, not copy; every edit's `oldText` is copied verbatim from `read` output, and an edit miss means re-read the region, not a wider match. (c) unknown script/CLI → read its `--help`/argparse block first; one turn of interface reading costs zero.
- Metric-design scar (2026-10-04, from the Phase 2 ablation post-mortem): every pre-registered metric ships with a written adversarial case — an answer that passes the metric while failing on merit (citing random chunk IDs passes resolve rate; keyword-stuffing passes a regex fact-check; a no-citation arm is unmeasurable, not perfect). If such a case exists, the metric is leaky — fix the metric before running, not the interpretation after. Three leaky metrics in one session cost a redesign.
- Plan-verification scar (2026-10-04, from the L0 router cleanup post-mortem): an implementation plan — written by an assistant, not the executing agent — was drafted from a log of an earlier file version, not the worktree. It assumed `## Projects + grades` existed in `AGENTS.md` when the section had never been there, so its "delete the generated list" step described work that does not exist. Step-0 reconnaissance caught it and commit C became "add the link" instead. Rule: before a plan asserts a target exists (a section, a file, a counter), verify it against the current worktree; a log, report, or earlier session's readout is not a worktree. The verification belongs to the plan's author, before the plan is handed to an executor.
- Commit-hygiene scar (2026-10-05, workspace-wide, promoted from ARL `EXPERIENCE.md` §8–9): read the **index, not just the working tree**, before any `git commit` — `git status --short` + `git diff --cached --stat`. Staged residue from a failed `agent_commit.py` run (or a half-finished staging) is what ships, not the tree. A failed `agent_commit.py` now rolls back its own staging (`unstage()` in ARL `scripts/agent_commit.py`, pinned by `tests/test_agent_commit.py::StagedResidueTests`); a raw `git commit` of one file can still ship unrelated staged files, so the index check is the caller's job. A stale generated view (`MAP.md is stale` advisory) is cleared at the FIRST signal it appears, not deferred to session end — an ignored advisory is how stale state gets read as current state later.
- Verification-scope scar (2026-10-05, workspace-wide, promoted from ARL `EXPERIENCE.md` §9): never narrow a verification to survive a timeout. If a full suite exceeds the tool's timeout, raise the timeout or run it in the background and get the full number — do not run a subset and report "N/N" with a footnote. A subset result is a claim about only those files; if a subset is genuinely what is in scope, say so and name every excluded file as "not verified". Timeout is a property of the tool, not of the claim.
- Mechanical tool-call scar (2026-10-05, from the droid Phase 2/3 post-mortem): `TodoWrite`'s `todos` is a **single plain-text string** of numbered lines — `1. [completed] task`, `2. [in_progress] task`, `3. [pending] task` — **not** a JSON array of objects (`{status: …}`), not an empty `{}`, and not nested objects keyed by `"t"`. It failed on those shapes at least 3× across the session, **and kept failing after round-2 feedback named it**, because the fix stayed a memory note, not a recorded rule. Two rules: (a) when a tool call fails on input shape, read the tool's schema/docstring once and copy the exact working shape — do not retry variants by feel; (b) a mechanical error that repeats after being reported is a process gap — record the working shape here (or in the tool's contract) so the next session pays for it once. The cost is re-paid context on every retry; a one-line scar prevents it.
- Report-state verification scar (2026-10-05, from the session-memory review loop): a session **reported success for code that did not exist** — "Level 1 telemetry implemented" while `memory_index.py` held no trace of it — and the following session ground ~30 reads (one file ~17×) trying to reconcile its inherited memory with the worktree, writing nothing. Two rules: (a) **a session report is a claim, not a state** — before planning, verify against the worktree with one command (`Grep`/`Select-String` on the key symbols), never from the previous report; (b) **the same range read 3× = stop** and check the file is not what you believe; past that point, reads add nothing and re-pay the whole prefix.
- Chrome 127+ App-Bound Encryption vs external cookie readers (2026-10-07): `notebooklm-py login --browser-cookies chrome` on Chrome 127+ reads from disk only unencrypted cookies (`NID`, `__Host-GAPS`), never sees `SID` or `__Secure-1PSIDTS`. Symptom: `server_info` → `authenticated: true`, `auth check --test` → `token_fetch: false`. `server_info` is a local report, not a network test. **Fix:** auth via CDP from a live Chrome session (`nlm login` in `jacob-bd/gemini-notebook-mcp-cli`), never via file read. Same pattern as `memory_eval.py` — local tool says "OK", the network path is broken.
- Profile ≠ session in `nlm` (2026-10-07): `nlm notebook describe` / `source list` without `-p` use the default profile. If the default is a different account than the notebook owner, Google returns `Authentication expired` — misleading, the session is valid. `doctor auth-replay -p <profile>` passes while `notebook describe` fails. **Fix:** `nlm login switch <profile>`. Same pattern as `server_info` in `notebooklm-py`: local check says OK, network says expired. Also: `nlm login --check` can say "valid" while every replay lane fails — only `doctor auth-replay` is truth. nlm 0.9.6 had a CSRF-recovery bug faking "expired" after ~8h; upgrade to 0.15.4+ (`uv tool upgrade notebooklm-mcp-cli`, profile survives).
- Do-not-build-wrapper-before-auth scar (2026-10-07): a previous agent burned ~40 turns building `notebook_push.py` + `notebook_mcp.py` on `notebooklm-py` while `token_fetch` was `false` from the start. Order is: **native auth test → one upload → wrapper.** Never reversed.
- AGENTS.md routing row = R13 cascade (2026-10-07): adding one row to the `Where to go` table shifted the token-efficiency section +1 and forced: regen audit block, prose shift 132→133 in the review report (7 spots), span 63-99→64-100, 3 EXEMPT changes (add 63/101, delete 102). Worse: editing the dated v7 report in place made a 2026-10-03 document describe a 133-line AGENTS.md that did not exist then. **Rule:** an AGENTS.md edit is never a 1-line change, it is a ≥3-file change; bundle it with a new report version (v7→`projects/_archive/reviews/`, v8 current in `docs/reviews/`), never rewrite the dated report. - Unclear prompt / Analysis ingestion scar (2026-10-11, from the goose evaluation report intake): when given an analytical document or report without an explicit executable directive, an agent must not guess intent, improvise, or answer with narrative essays ("framing instead of finding"). Rule: an unclear or directive-free prompt requires exactly one clarifying question before any tool call or state change. Furthermore, violating command prohibitions (such as `python -c`) or engaging in stale tool-retest loops without source changes reproduces the exact meta-problems the analysis critiques.
- Goodharting and destructive remediation scar (2026-10-11, from the goose evaluation review remediation): when an integrity check fails due to unexpected root folders containing valuable data or artifacts (like reports/), an agent must never silently delete them with rmtree to satisfy the gate. Rule: root data destruction without explicit owner consent is prohibited; a gate must not be passed by destroying the data it flags. Furthermore, repeating prohibited tool patterns (such as python -c) during remediation escalates failure.

## S53: Semantic coverage prog_cosine=0.60 nieseparowalny od rzeczywistego rozkładu oracles
- **Data**: 2026-10-11
- **Problem**: Implementacja pokrycia semantycznego z prog_cosine=0.60 w hybrid_eval.py / graphrag.py okazała się funkcjonalnie martwa (delta semantic ON vs OFF = +0.000 we wszystkich 4 konfiguracjach). Rzeczywiste cosine similarity dla oracles Q3 to 0.48-0.54, a dla Q2 to 0.54-0.56, czyli poniżej sztywnego progu 0.60.
- **Wniosek**: Próg 0.60 został dobrany arbitralnie powyżej rzeczywistego rozkładu cosine dla poprawnych węzłów. Poprawka Q3 opiera się faktycznie na PL_TO_EN_MAP (exact-match), a nie na bramce semantycznej.
- **Zalecenie**: Wymaga ponownej kalibracji progu, rezygnacji z bramki lub utrzymania jako feature flag OFF.

## S55: Wrażliwość progu cosine i ryzyko fałszywego sukcesu w kalibracji semantycznej (2026-10-11)
- **Problem**: Próby kalibracji `prog_cosine` w `oblicz_pokrycie()` (`0.60` -> `0.45` -> `0.54`) pokazują, że bramka semantyczna jest niezwykle wrażliwa na dobór progu: zbyt wysoki próg daje zero efektu (delta +0.000), a zbyt niski lub nieprecyzyjnie dobrany może prowadzić do regresji w pytaniach out-of-corpus (OOC) lub canary (odmowy przepuszczające fałszywe zapytania). Ponadto pomiary oparte na uproszczonych lub niepełnych mapach oracle ID nie odzwierciedlają w pełni pełnego spektrum 30 pytań extended eval.
- **Wniosek**: Kalibracja progu wymaga rygorystycznego grid-searchu na wszystkich 30+ pytaniach z pełnym audytem refusal/OOC oraz obowiązkowym uruchomieniem `verify_report.py` i skryptu domykającego sesję przed deklaracją sukcesu. Alternatywą jest Wariant 2 (rezygnacja z bramki semantycznej) lub Wariant 3 (feature flag OFF).

## S69: `close.py --dry-run` nie waliduje sesji, która wycofuje flagę (2026-10-16)
- **Problem**: `close.py --dry-run` (`dry_run()`, `scripts/close.py:210`) uruchamia kroki `diff-check`, `handoff-check` (`build_handoff.py --check`) i `integrity` **bez** wcześniejszego rebuild.
