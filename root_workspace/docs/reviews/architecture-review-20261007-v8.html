the entropy gate is blind in the one subtree the entropy lands in

Strong

Problem

R3 walks for proj in PROJECTS — project repos only — then does a second loop over ROOT.iterdir() catching zero-byte files at the root top level only. Between those loops sits ROOT/scripts/, which is neither. scripts/_scratch/ is therefore invisible to every gate and to git status, because .gitignore:18 hides it. 22 files, ~27 MB: sessions_dump.txt 12.0 MB, browse_all.html 8.0 MB, Kontynuacja-przy…json 5.4 MB.

The mechanism is the point: gitignoring a directory to stop it polluting git status also removed the only other thing that was watching it. One rule, two jobs, and the retention half was never written. There is no size, age or count policy for _scratch in AGENTS.md, CLAUDE.md, DECISIONS.md, or the gate.

Two tools, one unowned dir. v1 listed session.py:22 and agent_sessions.py:31 as bare OUTDIR lines and stopped there. That was the shallow reading. They are two independent tools — one extracts from the opencode SQLite db, the other aggregates across five agent harnesses — and they write overlapping artifacts into the same directory with no declared relationship: latest.md from session.py sits beside sessions_dump.txt and browse_all.html from agent_sessions.py, and the two refresh_*.bat files drive only the latter. So the dir has no single owner even informally — which is why no rule ever appeared. A retention contract is also the cheapest thing that would force the ownership question.

Deletion test. Delete the gate's residue logic: the complexity does not concentrate, it moves to R1, which would name scripts once and stop. Shallow — its interface (ALLOWED_ROOT plus seven suffixes) is about as large as its implementation, and it buys no leverage over the other run-scoped output dirs (.dgc-evidence/runs/, .forge/journal/, scripts/out/, ARL reflection/sessions/), each with its own bespoke ignore rule and its own bespoke prose rule in its own CLAUDE.md.

Solution

One retention contract shape, declared once per run-scoped output dir, reused by all of them: {path, owner, regenerable_by, max_bytes, max_age}. The gate computes declared-vs-actual and returns one of four verdicts — all four stated, including the case v1 omitted:

State Verdict Who acts
under budgetsilentnobody — ordinary work costs 0 attention
regenerable + over budgetadvisory, prints the regen commandnobody — the report says what to run
NOT regenerable + over budgetFAIL, naming the owner path whose author must declare a budget or a regen paththe author of that file — never an automatic delete
no declared ownerFAILhuman — this closes the ad-hoc-shell hole

The third row is the one v1 left open, and its absence mattered: unrecoverable bytes must never be auto-deleted by a gate, which is the same principle that makes ARL's check_evidence_guard.py refuse to remove a flagged artifact. Losing evidence to satisfy a budget is the failure mode check_workspace_integrity.py:166-169's own docstring warns about ("failing the build on it teaches people to delete their own evidence"). So the gate escalates to a human and the fix is a declared budget, not a deletion.

Field definitions (v3 — owner replaces v2's undefined owner_tool):

  • owner — a path to the script that writes into the dir, e.g. scripts/session.py. A path, not a role or a person, so the gate can check it exists. For scripts/_scratch/sessions/ this immediately surfaces that two tools write there — which is the finding above: the contract cannot be written until the ownership question is answered, and that is the point of asking.
  • regenerable_by — the exact command, or null. Never a prose description.
  • max_bytes / max_age — the budget. Absent means "no budget declared", which the third verdict treats as over-budget.
  • Escalation always goes to a human, but the human is named by the path: the verdict names the file whose author must declare a budget or a regeneration path. The verdict string is the accountability, so v2's "owner_tool's author" and "human" stop being two different answers.
Correction to the gate-line table (v3 label → v4 estimate → v5 measurement). Candidate 1's "prose removed" cell read "2 one-shot scripts + 1 superseded copy retired" — a label, not a count. v4 turned it into "~610 lines" and called that "counted now, from the files themselves". The reuse precedent, stated accurately

v1 said "working in production". That was wrong. Corrected, with evidence:

  • No caller. Absent from …/scripts/quality_check.py; absent from …/pipeline/WORKFLOW.md's phase-5 action list (which does list evict_stale.py:103 and check_eviction.py:104); no test references it. Its only Python appearance outside itself is a docstring mention at repair_graph_state.py:6.

So the reuse argument rests on the second bullet, not the first: the shape — compute a fingerprint, compare, refuse and say which assertion failed — has been debugged against real corruption, which is expensive and worth reusing. The wiring has never existed, which is the same disease as this candidate.

This is actually a stronger argument than v1's, and it is honest: the pattern is proven, the plumbing is missing, and candidate 2 is largely a plumbing change to a shape that already survived contact with a corrupt file.

Solution

Give flags typed, checkable claims and let the gate that already exists verify them. Four assertable frontmatter fields — supersedes:, asserts_sha:, asserts_path:, asserts_absent: — each resolved by --check:

  • does the sha exist (git cat-file -e) → the commit flags become self-checking;
  • does the path exist → HANDOFF.pre-migration.md, the deleted .forge/context.md, and every stale "next step" get caught by the gate instead of by the next cold session;
  • is this flag superseded → the four pairs resolve mechanically, and the older flag's fate is decided by a fact rather than by whoever noticed last;
  • does unassigned survive a staleness check → ownership stops being a value nobody maintains.

A flag whose claim fails is not printed as state — it surfaces as stale: <flag> <assertion>. Retiring it then becomes the obvious cheap action, which is what handoff/CONTEXT.md:36-37 asks for in prose and never gets. Note: this candidate would have caught HANDOFF.md:200's claim that skill_router.py "routes ralph intents" — ralph.py contains zero matches for skill or route. That is the sharpest available evidence that the gap is real and not hypothetical: a false claim about wiring is currently sitting in the generated view.

A claim lives in the same file as its subject, verified at the moment it is read. No flag can assert a sha that another flag's deletion invalidates.

Leverage

Reuses a shape already debugged against real file corruption (CONTEXT.md:176), so the expensive part — knowing what "refuse safely" means — is already paid for.

The gate, redesigned to be falsifiable

Withdrawn: "measure tokens before/after".

No router = 0 cost; router added = cost > 0 always. The comparison returns "cost" trivially, so it cannot fail and therefore cannot decide — and per the finding above, the baseline it would subtract from was never recorded.

Replacement — a gate that can come out negative:

The router earns its place iff it lets us delete the prose. The denominator already exists in the tree:

  • Numerator: tokens the router adds per session start — one subprocess over two pure functions.
  • Denominator: the 17 routing lines + 2 duplicate evidence lines of AGENTS.md it replaces, counted line by line in the audit above. Not the ~35 v3 claimed.
  • Kill condition: if the router lands and those lines do not shrink, it is pure added cost and gets deleted. That outcome is live, not hypothetical — the prose is the only thing currently making skills load despite disable-model-invocation, so deleting it without a working replacement would silently regress skill usage.
  • And the honest floor: a perfect router retires 17 lines, and a separate dedup pass retires 2 more (:85, :104) — 19 in all, from two different actions. Step 3 must survive 17, the number the router alone is answerable for.

This converts an unbounded value judgment into a bounded one: not "is routing worth it" but "is a 17-line manual mechanism worth more than its automated replacement". That has a checkable answer, and it can come out no.

What stays a judgment: whether the deleted prose was doing anything other than naming a skill. The classifier settles this per line rather than per block: :66, :68-69, :71-77, :78-84 and :86-90 all carry measurements or catalog content and are excluded from the gate entirely — 24 lines per audit_agents_md.py. Only :57, :58-64, :98, :100 and :102-108 are in scope. v3 asserted this exclusion without performing it; v4 performed it by hand and got the count wrong; v7 performs it in code, so a reader can run it and disagree with the rules rather than with an unverifiable number.
