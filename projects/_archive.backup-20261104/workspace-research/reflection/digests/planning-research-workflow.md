## Evidence

* **ICM filesystem as plan primitive — present.** `00_interpretable_context_methodology_folder_structu` defines ICM as replacing framework orchestration with filesystem structure — numbered folders as stages, markdown as interface. `00_icm_map` codifies the Five Rules (One Stage One Job; Plain Text as Interface; Layered Context Loading; Every Output is an Edit Surface; Configure the Factory, Not the Product). `00_plain_text_as_interface` and `00_one_stage_one_job` detail why single-responsibility stages with plain-text handoffs beat multi-purpose stages (focused context, clear accountability, Git-diffable). The current `stages/01_inbox`..`04_reflect/CONTEXT.md` + `CONTEXT.md` satisfy exactly this: per-stage Inputs/Outputs tables are the plan fragment.
* **But "stages as plan" ≠ "plan as artifact".** `00_from_plan_to_action_how_well_do_agents_follow_th` is the decisive counterweight (21,120 SWE-agent trajectories, 4 LLMs, 8 plan variations): without an explicit ordered plan agents fall back to incomplete, overfit internal workflows; an explicit plan improves resolution; a *subpar* plan hurts more than no plan; early-stage task-relevant additions that misalign with the model's internal strategy degrade performance; periodic plan reminders mitigate violations. The KB's `stages/*/CONTEXT.md` alone leave phase order, entry/exit gates, and ordering implicit — exactly the gap that study predicts causes compliance drift.
* **Decomposition must be adaptive, not static.** `00_adapt_as_needed_decomposition_and_planning_with` (ADAPT): recursively decompose a sub-task only when the executor signals inability — adapts to both model capability and task complexity (+28–33% over static plan-and-execute). The corpus retrieval `ai-planning-htn-pddl` supplies the classical substrate: HTN task networks + PDDL/HDDL methods as the decomposition representation ICM stages are implicitly using. Current `route.py`/`spawn.py` plans are static: tag intersection `ORDER BY id` with fixed `--limit`; no threshold-triggered split.
* **Memory ↔ planning coupling.** `00_agent_memory_hierarchies` establishes the write–manage–read loop coupled to perception/action (POMDP cycle); implication: treat `knowledge/corpus/*.md` + `graph.db` as the persistent hierarchical store (Layer 3) and `ask.py` + digest injection as the managed read path. `00_persistent_memory_hierarchies_agents` and `00_memory_for_autonomous_llm_agents_mechanisms_eval` reinforce that short vs long is insufficient — evaluations must couple memory with action (MemBench/MemoryAgentBench). `00_self_evolving_world_models_for_llm_agent_plannin` adds the world-model layer: plan-relevant state must persist beyond one-shot retrieval so reflection informs the next plan. `00_plan_persistence_context_window_compaction` identifies the concrete failure mode — plan text lives in the context window and compacts away mid-trajectory — i.e., plans don't persist unless externalized as files.
