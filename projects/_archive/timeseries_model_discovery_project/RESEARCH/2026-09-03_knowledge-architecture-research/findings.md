## 3. The field: inject vs query

### 3.1 Anthropic, "Effective context engineering for AI agents" (2025-09-29, fetched)
- Context = "a critical but **finite resource**"; models have an **attention budget**; every token depletes it; performance degrades "well before the window fills" (they cite Chroma's context-rot work).
- Guiding principle: "**find the smallest possible set of high-signal tokens** that maximize the likelihood of some desired outcome."
- The field is converging on "**just in time**" retrieval: agents keep *lightweight identifiers* (file paths, stored queries, web links) and load data at runtime via tools; "**progressive disclosure**" — each interaction yields context that informs the next decision; agents "keep focused on relevant subsets rather than drowning in exhaustive but potentially irrelevant information."
- **The trade, stated explicitly**: "runtime exploration is slower than retrieving pre-computed data. Not only that, but opinionated and thoughtful engineering is required to ensure that an LLM has the right tools and heuristics… Without proper guidance, an agent can waste context by misusing tools, chasing dead-ends, or failing to identify key information."
- **The verdict is hybrid, not either/or**: "In certain settings, the most effective agents might employ a hybrid strategy, retrieving some data up front for speed, and pursuing further autonomous exploration at its discretion. The decision boundary for the 'right' level of autonomy depends on the task. **Claude Code is an agent that employs this hybrid model: CLAUDE.md files are naively dropped into context up front, while primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time.**"
- Long-horizon: compaction, structured note-taking (write notes out of context, pull back later), sub-agents (deep work isolated; condensed 1–2k-token summaries back).

### 3.2 Chroma, "Context Rot" (2025-07-14, 18 models, 194,480 LLM calls, fetched)
- **Every model degrades as input length grows**, on intentionally simple tasks; degradation is driven by input length and distractors, not window limits.
- **Distractors**: "Even a single distractor reduces performance relative to the baseline (needle only), and adding four distractors compounds this degradation further"; impact is **non-uniform** across distractors and **amplifies as input length grows**. Claude-family models abstain under ambiguity; GPT-family hallucinate confidently.
- **Needle-question similarity**: the lower the semantic similarity between the question and the answer, the faster degradation with length — i.e. *the more the injected fact is a paraphrase of the task rather than identical phrasing, the more it must compete for attention*.
- **Structure matters**: logically structured haystacks consistently *hurt* vs shuffled — context organization is not neutral.
- **LongMemEval (focused ~300 tok vs full ~113k tok)**: focused input beats full input **across all model families** — forcing the model to do retrieval inside a long context is strictly worse than being handed the relevant slice. (Complement to Anthropic: the model is worse at in-context retrieval than at reasoning over a curated slice.)

**Direct application to this workspace**: the ts-brain.ts block is ~8 static lines (~200 tokens) injected into *every* omp session. For a TS task it is high-signal; for any non-TS session it is a *permanent distractor* — and per Chroma, its harmful effect grows with total context length. GCC's 400-token *prompt-scoped, retrieval-produced* injection is the same order of magnitude but (a) scoped to the current prompt, (b) produced by code at submit time, (c) zero cost when nothing matches (their hook can return empty context).

### 3.3 RAG vs agent memory (framing sources, fetched via search snippets — see references)
Consensus framing across four sources (vectorize, kronvex, redis, zylos survey): RAG = stateless retrieval from a corpus; agent memory = stateful, learned from experience, temporal; **production agents use both**; the real design axis is *when* (pre-inference vs just-in-time) and *where* (system prompt vs message vs tool result) knowledge lands. No source found endorses *maximal* injection; the workspace's `brains/CONTEXT.md` boundary ("brains are read-consulted libraries, not the agent's memory; native memory = quick facts") matches the field consensus and is retained as-is by this commission.

## 5. Multi-brain management (Q2) — patterns observed

1. **Registry + deterministic dispatcher** (this workspace, already built): `brain_router.md` table + `topics.md` keyword sets + `ask.py` scoring + `build_brain.py` (rebuild router from folder scan) + per-brain `verify_sync.py` drift detection. This is a *superset* of what GCC ships (GCC has one brain; its multi-hop answer is structural, not federated).
2. **One domain = one brain** (GCC's "start with rag/, move up when your questions chain facts" = an *escalation* ladder within a brain; the workspace generalizes it to *across* brains). Ownership table doctrine from `chief-of-staff-crew` ("who owns which files") transfers directly: each brain owns a folder, a topic vocabulary, a sync pipeline, and a row in the router.
3. **Budget the injection per brain** (Chroma + GCC): the healthy ceiling observed is ~400 tokens of *injected* knowledge, and it must be prompt-scoped. With N brains, injection must be *routed* (at most one brain's slice per prompt), never stacked. The workspace's dispatcher already computes the routing; it just never feeds an injector today.
4. **Staleness is the dominant failure mode, not retrieval quality**: the workspace has three logged incidents (injected line stale; chunk-01 protocol stale; FTS5 syntax crash). The existing countermeasures (marker regions + `sync_brain.py` regeneration + `verify_sync` + chunk-04-only-auto-sync invariant) are the management system; GCC adds the principle of **build-time intelligence** ("spend intelligence at build; answer from structure") — model distillation happens at index/write time (their extraction prompt, their digest), never in the hot path.
5. **Two-copy duplication is the known anti-pattern** (ts-brain.ts ROOT + project copy; incident `2026-09-02_extension_injection_staleness.md`): the durable fix direction from the sources is *single source + regeneration* (build_brain.py already does this for the router; the extension copies are the residual violation) or *elimination* (cutover — see open decision in `PROGRESS.md`).
6. **Memory isolation vs shared corpus**: the "One Model, Many Minds" pattern (persona-specific prompts, memory isolation, lightweight orchestration) was cited in a Build Day report (shipsolid) but the source 404'd this session — see open questions. The workspace's analog is already the split: native memory (per-project, `~/.jcode/memory/`, NOT in repo) vs brains (curated, git-tracked, in repo). That split is worth stating as an invariant: *volatile personal state outside the repo; durable curated knowledge inside it.*

**Answer to Q1** (grounded, not designed — 02_research records what the sources say): the field's convergent position is **hybrid C**: a small, static, *routed* always-on slice (protocol invariants + where things live — the workspace's existing AGENTS.md/overlay + ≤400 tok), deep facts on demand through a deterministic dispatcher, and prompt-scoped dynamic injection *only where the harness provides a prompt-time channel* (omp `before_agent_start`, Claude Code `UserPromptSubmit`). **Answer to Q2**: keep the registry architecture; its invariants, per the sources: (1) one domain per brain, ownership tabled; (2) deterministic routing (keyword/structure, no LLM in the loop — workspace doctrine, GCC-demonstrated); (3) build-time intelligence (distil at build/digest, never in the hot path); (4) one source + regeneration for anything duplicated (build_brain.py pattern; kill or regenerate the two-copy extension); (5) per-brain injection budget ≤ ~400 tok and routed, never stacked; (6) staleness as a first-class invariant (verify_sync + auto-sync marker regions for volatile facts like leaderboards); (7) volatile memory outside the repo, curated brains inside.

**Answer to Q3**: hooks are the *deterministic layer around* knowledge, not the knowledge channel, in Jcode: (a) `pre_tool` gates = contract enforcement (prompt-router `gate.py` port: refuse-done-without-proof, refuse-protocol-violation); (b) observers = pipeline glue (sync/verify after changes, reflection nudges at turn_end, drift alarms); (c) in omp/CC, the same code additionally *can* carry prompt-scoped injected facts — design the injector as a standalone script (GCC's `recall_hook.py` shape: stdin prompt → JSON context out) so it is harness-portable.

### 7.2 The Haiku row is capability-conditional — the field says so too
The single load-bearing GCC datum is Haiku: `1 of 3` hops searching, `3 of 3`
through the graph. §2.1 and §6 already warned this is one model, one question,
one small corpus. Two 2026 papers now **independently confirm the mechanism**:
- **Pandey, "Can Small Language Models Use What They Retrieve?"**
  (arXiv 2603.11513, 360M–8B models, NQ+HotpotQA, oracle-retrieval design):
  with retrieval *guaranteed* to contain the answer, models ≤7B still fail
  85–100% of the time on questions they cannot answer alone; the 7B model
  extracts the correct answer only **14.6%** of the time under oracle
  retrieval; the dominant failure mode is **irrelevant generation (61–100%)** —
  "the model ignores the provided context completely." Their conclusion: for
  sub-7B models the RAG bottleneck is **context utilization, not retrieval
  quality**. This is the same axis GCC's Haiku row measures, measured at scale:
  a small model is given good context and still cannot work it. GCC's fix
  (traverse in code, inject the resolved facts) removes the *reasoning* load,
  not the retrieval load.
- **The same paper's hybrid leg is a caution, not a corroboration**: with
  RRF k=60 on a 500K-passage corpus, hybrid **underperforms pure dense**
  retrieval (hit@5 14.9% vs 16.3%) — "the BM25 signal adds noise at this
  corpus scale." GCC's `rag/` uses RRF k=60 over a *notes* corpus, orders of
  magnitude smaller. The finding bounds the claim: RRF's benefit is
  corpus-scale-dependent, and GCC's scale is the one where it helps.

### 7.3 Retrieval, not write sophistication, is the dominant factor
- **Yuan et al., "Diagnosing Retrieval vs. Utilization Bottlenecks in LLM
  Agent Memory"** (ICLR 2026, arXiv 2603.02473; 3×3 factorial: raw chunks vs
  Mem0-style extraction vs MemGPT-style summaries × cosine/BM25/hybrid+rerank;
  LoCoMo, 1,540 questions): **retrieval method drives 14–23 accuracy points,
  write strategy only 3–8**. The cheapest write strategy — raw chunks, **zero
  LLM calls** — matches or beats both lossy alternatives under every retrieval
  method (81.1% best overall, Basic RAG + hybrid). Retrieval precision
  correlates with accuracy at **r = 0.98**. Failure analysis: retrieval
  failure 11–46% of questions, utilization failure stable at 4–8%,
  hallucination 0.4–1.4%.
- **Direct tension with GCC's `digest/`+`distil.py`**, which spends a
  `claude -p` call per note to distil questions+summary+rule+quote at write
  time. Yuan et al. would predict that spend buys ≤8 points and can be net
  negative (lossy compression "discards contextual nuances useful at inference
  time"). GCC's own guardrail is the reason it survives the objection:
  `distil.py` verifies the quote word-for-word
  (`normalise(quote) not in normalise(body)` → drop) and indexes the entry
  *alongside* the raw chunk, not instead of it — the source note stays
  fully retrievable. The distilled entry is an added retrieval surface
  (question-shaped anchors), not a lossy replacement. That is precisely the
  design Yuan et al. do not test: *lossless write + supplementary
  query-shaped index*.

### 7.4 "Fixed at any corpus size" survives, with a named boundary
- **Fan et al., "Do We Still Need GraphRAG?"** (arXiv 2604.09666, RAGSearch
  benchmark): agentic search (dynamic multi-round retrieval) "substantially
  improves dense RAG and narrows the performance gap to GraphRAG,
  particularly in RL-based settings." But: **"GraphRAG remains advantageous for
  complex multi-hop reasoning, exhibiting more stable agentic search behavior
  when its offline cost is amortized."** GCC's design is the extreme point of
  that trade: offline cost = one modelling pass over 8 docs; online cost = a
  2 ms SQL walk whose output size does not grow with the corpus.
- **Han et al., "RAG vs. GraphRAG: A Systematic Evaluation and Key Insights"**
  (arXiv 2502.11371): under a unified protocol the two paradigms have
  "distinct strengths ... across different tasks"; combining them beats
  either alone. GCC's `rag/`+`graph/` split is that combination, and its
  README ladder ("Start with rag/. Move up when your questions chain facts
  across documents and you are willing to model for it") is the
  task-shape decision rule both papers say is the actual question.
- **Cost asymmetry is real and is the reason the design is cheap**:
  Microsoft's LazyGraphRAG defers all LLM summarization to query time, claiming
  indexing cost identical to vector RAG and >700× lower query cost than full
  GraphRAG global search. The field's summary of full Microsoft GraphRAG:
  "The graph isn't expensive to use. It's expensive to be born" — full
  GraphRAG indexing is ~1000× the price of vector indexing. GCC inverts the
  priority: it spends a *little* at build (one extraction pass, a quote-checked
  distil per note) and makes the query path a pure SQL walk. GCC is not a
  cheaper GraphRAG; it is a different point on the axis — **no community
  detection, no summaries, no LLM anywhere in the query path.**

### 7.5 The deterministic-identity choice is an industry pattern, not a trick
GCC's `entity_id = uuid5(NAMESPACE_OID, f"{type}:{normalised name}")` makes
"Ops Manager" in doc 1 and doc 4 the same node with no lookup and no ML.
Independent corroboration: **cognee** (topoteretes/cognee) ships a migration
named `namespace_entity_type_node_ids.py` and a merged PR titled
"deterministic key-based entity dedup via merged_into edges (SDK-208)" —
the same type+name-namespaced deterministic-key dedup, at framework scale.
The pattern's payoff is exactly what GCC's recall relies on: traversal is
deterministic because node identity is content-addressed, which is what makes
the injection size bounded and the build reproducible.

### 7.6 Hybrid search in SQLite is a recognized primitive, not an oddity
**Breuer, "SQLite is Enough"** (arXiv 2608.24060, scrydb): FTS5 for lexical,
sqlite-vec for semantic, rerank+fuse for hybrid — "a lightweight solution for
downstream tasks in IR or agentic search," evaluated on IR benchmarks with
latency/efficiency trade-offs. GCC's `rag/` (FTS5 BM25 leg + fastembed
bge-small-en-v1.5 meaning leg, RRF k=60) is the same architecture; the paper
establishes it is a studied primitive with published trade-off data, backing
the workspace's own FTS5-based `ask.py` choice.

### 7.7 Grounding, verified on disk — the workspace is already this design
Read from the INBOX dump's own source, not the README:
- `src/schema.sql` = 3 tables (`entities(id TEXT PK uuid5, name, type,
  description, source_doc)`, `relations(source_id, target_id, predicate,
  source_doc)`, `aliases(entity_id, alias)`).
- `src/recall.py`'s `WALK` is a recursive CTE; seeds = entities whose name or
  alias appears in the question (`\b` regex over name+alias tables); k-hops
  default 3, `top_k` 8; returns triples *plus entity descriptions* because
  "the conditions live on the entities, not the edges"; on no seeds it returns
  `(no memory matches for this prompt)` — a **loud failure**, never a guess.
- `rag/distil.py` runs `claude -p` in an **empty temp dir** with
  `MEMORY_STARTER_CHILD=1` and `CLAUDE*` env vars stripped — the child has no
  project, no settings, no parent hooks. This is the same isolation doctrine
  as the workspace's two-tier `workspaces/<brain>/` split (orchestrator clean,
  brain workers inject only in their own cwd).
- `digest/session_end.py` fires on **SessionEnd AND PreCompact** with distinct
  timestamps — one long session can close twice, "once before a compaction and
  once at the end, and neither half may overwrite the other."

**Correspondence to this workspace** (each pair verified against local code):
| GCC element | Workspace equivalent | Same intervention at different grain |
|---|---|---|
| `recall.py` SQL walk over `graph.db` | `knowledge/graph/ask.py` over FTS5 corpus | query a built structure instead of re-reading files (the `query-over-read` lesson) |
| `entity_id` = uuid5(type+name) | corpus chunk id = stable handle | content-addressed identity → deterministic build, bounded output |
| closed ontology before docs | `CONTEXT.md` per folder + routing tables | fix the vocabulary first; the structure is then walkable |
| conditions on entities, not edges | `source:` provenance on chunks | carry the qualifiers with the fact, not on the join |
| distil quote-must-appear-word-for-word | `check_reflection.py` citation gate | no unsourced claim survives; a missing quote/`source:` drops the entry |
| `claude -p` in empty temp dir | `workspaces/<brain>/` two-tier isolation | the child reads only what you hand it |
| `PreCompact` double-close | compaction-variance lesson (2026-09-16) | a session that compacts closes twice; keep both halves |
| in-code transcript filtering before model | masking-beats-summarization finding | drop tool calls/results/dumps before any model reads |
