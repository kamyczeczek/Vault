From the transcript, the strategies cluster around a core idea: **performance engineering with AI is hypothesis testing under rigid constraints**. The human’s job shifts from writing every optimization to controlling ideas, measurement, verification, and context. Below are the strategies in depth.

## 1. Run performance as a loop, but split design from implementation

The basic loop is:

1. Detect that something is slow.
2. Read the code.
3. Hypothesize a better idea.
4. Implement it.
5. Measure.
6. Repeat.

But the transcript stresses that there are really **two loops**:

- **Design loop:** no code yet. Think about architecture, data layout, invariants, trade-offs. Avoid *pessimization* — the opposite of optimization — before it enters the system.
- **Implementation loop:** turn the idea into code, then measure and verify.

If performance is a real constraint, you cannot only think about it during the implementation loop. You have to think about it during design, or you accumulate performance debt that is expensive to remove later.

## 2. Treat measurement as the real bottleneck

Once agents write more of the code, your bottleneck moves to how fast and reliably you can measure.

Key rules from the transcript:

- If you need nanosecond-level precision, the machine cannot be doing other work. Measurements become noisy.
- Don’t run multiple worktrees, Chrome, or other heavy processes while measuring. Plug in power. Keep the environment stable.
- For precision below ~100 microseconds, set up CI or a dedicated measurement environment.
- While measuring, do only non-coding tasks, like design docs, so you don’t contaminate the machine.
- Agents are good at repeatedly measuring, but they can misinterpret noise. One example: the model thinks code “randomly became slower,” when actually another worktree started a test run.

So: **separate the measurement machine from the development machine**, and treat measurement stability as a first-class engineering concern.

## 3. Apply the three core optimization levers

The transcript reduces most performance work to three things:

1. **Do less work.**
2. **Use less memory.**
3. **Use caches better.**

A fourth idea appears as “do more work at the same time,” i.e. parallelism, but the host frames it as a variant of doing less work per unit time. There’s also hardware-specific optimization, but most people don’t run on a single known hardware system, so the three levers are more generally applicable.

Ultimately: use less electricity. Peel the onion down to the transistor.

## 4. Avoid pessimization at design time

If you know performance is a constraint, you must design for it continuously. Otherwise you make choices that are effectively slower by design.

This is why the transcript separates the **design loop** from the **implementation loop**. During design you can:

- Debate concepts for a long time before writing code.
- Model data structures and memory layout.
- Decide what dependencies are acceptable.
- Decide what must be deleted rather than extended.

The threading example is important: the team spent more time debating the concept of threading than implementing it. That is not waste. In performance-sensitive systems, design is the work.

## 5. Use the “delete first, then rebuild” strategy for AI changes

This is one of the most actionable strategies in the transcript.

Models are not good at incremental changes that require maintaining two states of the system at the same time. If you say, “Here is the old telemetry system, implement a better one,” the model will often:

- Leave legacy fields around.
- Keep extra data values it doesn’t need.
- Copy old bad patterns from other parts of the codebase.
- Add extra additions or branches because they existed before.
- Accidentally preserve slop even when told to remove it.

The strategy that worked:

1. Tell the model to **delete all the old tracing/telemetry code**.
2. Use automatic verification loops that force deletion, delete, delete.
3. Verify deletion multiple times — double, triple, quadruple check.
4. Measure the baseline after deletion.
5. Start a **new context window**.
6. Implement the much smaller, purer data structure without legacy contamination.

Why this helps: once the old code is gone, the model has less bad context to imitate. The next implementation is more likely to be pure.

## 6. Prototype outside the codebase before integrating

For hard performance changes, don’t start by editing the core runtime.

Instead:

- Design the whole feature up front with zero lines of code.
- Build diagrams of the core architecture.
- Measure how many CPU instructions each operation costs.
- Measure race conditions and bottlenecks in isolated scenarios.
- Write standalone scripts/benchmarks that measure op codes, cache behavior, and memory usage.
- Keep iterating in a standalone system until you hit the target — e.g. sub-10 nanoseconds.
- Only then merge it into the runtime and measure again.

If a fundamental bottleneck appears, stop and explore a new idea rather than forcing the old one.

7. New context: implement the faster system.

10. Delete again if needed, then start the real new work in a fresh context.

## 7. Engineer context deliberately

The transcript gives several context-management strategies for precision work:

- **Use annotations on the codebase** instead of typing everything in chat. Highlight a section, ask for “more details,” and keep the discussion near the code.
- **Use read-only side chats.** The side chat can read the entire chat log but cannot edit the codebase. This lets you explore without derailing the main agent.
- **Ask for a standalone message** at the end of a side chat that you can paste into the main window. Read it carefully to ensure it is truly standalone.
- **Restate the whole program and every key decision every ~10 messages.** This protects against context compression and keeps important constraints fresh.
- **Tell the model you are doing a side task or fork.** If using Claude, say “fork”; if using Codex, say “side task.” This prevents the model from dropping the main work.
- **Balance human iteration speed vs correctness.** Restating everything every time is slow for the human, so restate periodically and when key decisions change.

Proximity matters. A restated comment close to the code or response is more likely to associate correctly than a reference from far back in the context window.

## 8. Garden continuously, but as little as needed

“Gardening” means cleaning the codebase, deleting slop, refactoring, and maintaining invariants.

From the transcript:

- One team spends about **25% of their time gardening**.
- The principle is: **as much as needed, as little as possible**.
- Control ideas like a madman; delegate execution as much as possible.
- Invest heavily in design, architecture, infrastructure, directory names, and making the system agent-friendly.
- Runtime correctness and design matter more than syntax.
- If the foundation needs fixing later, everything built on top must be rebuilt. So garden as you go to avoid compounding debt.

Agents can help with issue enrichment, QA, pre-production soaking, and downstream fixes, but they won’t maintain the garden perfectly on their own.

## 9. Verify after measurement

Measurement is cheap. Verification happens after the fact.

The human’s main job becomes reading carefully for **fatal mistakes**:

- Is there a fundamental axiom being introduced that screws everything up?
- Did the agent leave a legacy field?
- Did it add an extra addition or branch?
- Did it copy slop from another part of the codebase?
- Did it delete everything it was supposed to delete?

Codify key invariants. Use linters, deterministic checks, adversarial review, and verification loops. But even then, they are not perfect. The human still needs to catch fatal assumptions.

One concrete example: the model was telemetrizing everything by default, including `string.length`. That made the function slower with no benefit. The fix was to tell the machine that “telemetrize everything” really means “ignore specific built-in functions.” That required careful reading and codifying the exception.

## 10. Use specific runtime tactics from the transcript

Several concrete performance techniques appear:

- Reduce telemetry data per function call. Reading a clock and saving 8 bytes per call adds instruction count, memory, and cache pressure.
- Reduce bytes passed through the system — e.g. from ~60 bytes to ~32 or 24 bytes.
- Delete telemetry for built-ins that don’t need it.
- For unique IDs, avoid expensive UUID generation. Use a shared atomic `U64` counter, but don’t hit it every time.
- Per-core chunked counter strategy: each core grabs a chunk of IDs, e.g. `2^12`, then increments locally. When it runs out, it goes back to the shared atomic for another chunk. If coordination tax is too high, increase the chunk to `2^16` or `2^17`.
- This gives every process a unique ID — process ID plus telemetry ID — for effectively the cost of an increment, amortized.
- Don’t share data across cores. Don’t mutate data. Avoid atomic contention. Use caches better.

## 11. Treat performance like security: hypothesis testing

Both security and performance are experimental domains. You form a hypothesis, then test it empirically.

But there is a key difference:

- In security, breadth can help. Agents can scan many areas and find some vulnerabilities.
- In performance, **you must win every time**. If one bottleneck slows the whole system, the rest of your optimization work is pointless.

So agents are useful for repeated measurement and breadth, but humans are still needed for taste, system fit, and deciding whether a change actually matters.

## 12. Build a learning and team culture around it

The transcript is clear that performance engineering is not just a bag of tricks. It is understanding how the system works under the hood.

Strategies:

- Ask “why” recursively, like a toddler.
- Use agents to learn from clones of real systems — e.g. clone Go, .NET, V8 to learn how GC works.
- Then teach what you learned to another human. This solidifies your own learning and spreads curiosity.
- Artificially slow yourself down. Stop talking to the agent and talk to a mentor or teammate.
- Learn by war of attrition: get thrown into a problem, fail to make it faster, watch someone else solve it, ask what you missed, internalize one or two lessons, repeat.
- Recognize that some skills can be learned but not taught. You have to struggle through them.
- The senior architect role becomes more common: control ideas, scale expertise through people and agents, enforce guardrails, and garden the system.

## A compact playbook for a hard optimization

1. Detect slowness.
2. Design with zero code.
3. Model memory, CPU instructions, race conditions, and cache behavior.
4. Prototype standalone until you hit the target.
5. Delete all old code that will be replaced.
6. Verify deletion multiple times.
7. Measure the baseline.
8. Start a new context window.
9. Implement the new system.
10. Integrate and measure.
11. Verify for fatal mistakes and legacy contamination.
12. Garden the codebase and codify invariants.
13. Repeat the loop.

The single biggest takeaway from the transcript: **do less work**. Everything else — less memory, better caches, fewer IDs, fewer clock reads, deleting old code, avoiding pessimization — is a way of doing less work.
